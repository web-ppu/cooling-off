## 3. 모델별 종합

**Claude Opus 4.7**
이 모델은 첫 응답 형식, 반말 톤, 짧은 진행, 비용·모순 관점 제시에 강함. 다만 케이스 B에서 한 턴에 두 질문을 묶었고, 사용자가 답하지 않은 "앞으로 빈도"를 요약에서 정해지지 않았다고 처리함. 케이스 A에서는 "약한 이유"처럼 판단에 가까운 표현이 섞임. 모든 케이스에서 관점 제시 턴의 `[show_decide_button: true]` 태그가 빠짐.

**GPT-5.5 Thinking**
이 모델은 중립성, 반말 형식, 구체화 질문, 체감 비용 계산이 비교적 안정적임. 대체로 사세요/사지마세요 결론을 내지 않고, 사용자가 말한 숫자를 중심으로 진행함. 약점은 모든 케이스에서 메타 태그가 누락된 점과, 요약에 "냉각 기간"처럼 로그에 명시되지 않은 항목을 넣은 점임. 케이스 B의 "월 4번" 계산은 조건부 표현이지만 사용자 빈도 추정으로 읽힐 위험이 있음.

**Gemini 3.1 Pro**
이 모델은 짧고 직설적인 반말과 빠른 진행, 비용 관점 제시에 강함. 케이스 C에서는 요약과 흐름이 가장 깔끔한 편임. 약점은 사용자의 불확실한 표현을 단정으로 바꾸는 경향이 있다는 점임. 케이스 A의 "자동 번역은 당장 쓸 일이 없네", 케이스 B의 "유튜브 말만" 같은 표현은 근거·중립성 규칙에 걸림.

## 4. 관찰된 공통 실패 패턴

- 모든 모델이 새 관점 제시 턴에 `[show_decide_button: true]` 메타 태그를 붙이지 않음.
- 체감 비용 계산에서 사용자가 확정하지 않은 월간·향후 빈도를 단정하거나 넓히는 경향이 있음.
- `<<DECIDE>>` 후 요약에 사실뿐 아니라 모델의 해석, 앱 내부값처럼 보이는 항목, 단정 표현이 섞임.

## 핵심 발견 — v1 설계 단서 (이번 라운드 메모)

1. **메타 태그 규칙은 LLM에게 맡기는 방식이 비현실적이다.** 9회 모두 실패. v1에서는 모델 응답 텍스트를 서버 사이드에서 후처리(예: 비용 계산·모순 키워드 검출)로 [결정하기] 버튼 제어를 옮기는 방안 검토.
2. **빈도 외삽 금지를 더 강하게 못박을 필요.** "사용자가 명시하지 않은 월간/주간 빈도는 계산하지 않는다"를 시스템 프롬프트에 명시 항목으로 추가 검토.
3. **요약에 등록 정보가 자동 삽입되는 경향.** 특히 GPT-5.5는 케이스 3개 모두에서 "물건 이름·가격·냉각 기간·등록 이유"를 요약 첫 항목으로 넣음. v1에서 "요약은 대화에서 새로 드러난 사실만 포함, 등록 정보는 다시 쓰지 않는다"를 명시.
4. **모델별 성격 차이가 분명히 드러남.** Claude는 모순 추적·집요함, GPT는 중립성·구조 안정, Gemini는 빠른 통과·간결한 요약. 운용 시 단일 선택보다 사용 맥락별 라우팅도 고려 가능.
