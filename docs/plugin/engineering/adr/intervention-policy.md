## 1. 맥락 (Context)

브라우저 확장의 핵심 가치는 *모든 구매를 막는 것*이 아니라 *충동·후회 가능성이 높은 구매*에 한정해 식히는 시간을 주는 것이다. 정책이 부재하면 생필품·식료품·반복 구매에도 모달이 떠 사용자가 확장을 삭제할 위험이 크다는 리뷰어 피드백(2026-05-25)이 있었고, 이에 따라 V1 정책을 사전에 고정해야 한다.

## 2. 결정 (Decision)

PRD §7.1에 다음 네 축으로 V1 정책을 명시한다. 이 ADR은 그 결정의 근거 데이터를 담는다.

- **트리거 조건**: 바로구매·구매하기·결제 진행 버튼만. 장바구니·찜하기는 V1 제외.
- **제외 조건**: 카테고리 자동 분류는 V1 미지원(휴리스틱 false-positive 위험). 가격 기반 자동 제외는 V1 미지원(본 서비스 cooling tier가 5만원 이하도 1일 cooling을 부여하므로 "cooling 미적용 가격대"가 없음 → 임의 임계는 정책 불일치). 사용자 명시 제외 도메인·URL은 통과.
- **빈도 제한**: 동일 URL 1회 (DB unique index가 강제). 도메인 / 전역 일일 cap 없음 — 빈도는 사용자 제어로만.
- **사용자 제어권**: 사이트 on/off 토글, 24h snooze (도메인 단위, 누른 시점부터 24시간), URL skip list (영구), 전체 비활성화 (Chrome UI). 4개 컨트롤은 OR 결합 — 하나라도 매치하면 모달 안 뜸.

상세 사양은 PRD §7.1을 권위 소스로 둔다.

## 3. 근거 — 유사 확장 비교

> 조사 방법: Chrome 웹스토어 등록 정보 + 공개 소개 기사·리뷰 기반 데스크 리서치 (2026-05 기준). "shopping pause / cooling off / delay purchase / impulse" 키워드로 발견한 5종을 (a)트리거·(b)제외·(c)빈도·(d)제어·(e)가격 게이트 축으로 정리. "미공개" 표기 항목은 실제 설치로 추후 보강한다.

| 확장 | (a) 트리거 조건 | (b) 제외/카테고리 처리 | (c) 빈도 제한 | (d) 사용자 제어권 | (e) 가격 게이트 | 비고 |
|------|------|------|------|------|------|------|
| **Icebox** | 지원 쇼핑몰의 "구매/Buy" 버튼을 자체 버튼으로 치환 — **버튼 단위 인터셉트** | 카테고리 분류 없음. 지원 사이트 고정 목록(Amazon·eBay 등 400여 곳)에서만 동작 | 없음 (대상 구매에 일괄 적용) | cooling 기간 사용자 지정(최대 30일+), 도구바 아이콘 → "Let me buy this" 즉시 구매 override | 없음 | cooling-then-buy 모델이 우리와 가장 유사. 일부 버전이 "절약 금액 합산"을 노출 — 우리가 의도적으로 피하는 게이미피케이션 |
| **Impause** | 쇼핑 사이트 진입 감지 시 "정말 필요해?" 팝업 — **사이트 단위** | 신뢰 사이트 exclusion list (사용자 추가) | 명시적 cap 없음 | Snooze(임시 비활성), 사이트 24h 차단, exclusion list | 없음 | 사용자 제어권 축이 우리 설계(on/off·snooze·skip)와 가장 근접 |
| **Checkout Chill** | 체크아웃 페이지 자동 감지 — **페이지 단위** (버튼 아님) | 카테고리/사이트 제외 미공개 | **결제 세션당 1회** ("once per checkout" 기억) | 가격 비교용 Amazon/eBay 검색 버튼. 명시적 snooze/disable 미공개. 100% 로컬 동작 | 없음 | 빈도 cap("결제당 1회")이 우리 "동일 URL 1회"와 같은 의도 |
| **Pause** | 쇼핑 사이트 진입 시 30초 인터스티셜 차단 — **사이트 단위** | 200여 개 사이트 대상, 사용자 사이트 목록 | 진입할 때마다 (시간 기반, 30초) | 30초 후 통과, 사이트 목록 편집 | 없음 | 버튼이 아니라 사이트 진입을 막아 반복·생필품 구매에도 뜸 — 우리가 피하려는 노이즈 패턴 |
| **일반 사이트 차단기** (StayFocusd·Cold Turkey 류) | 사용자 지정 사이트 진입/시간 초과 시 **전면 차단(hard block)** | 사용자 지정 도메인 목록 (쇼핑 전용 아님) | 일일 시간/스케줄 기반 | 도메인·시간·스케줄 사용자 지정 | 없음 | 구매 인지 없음. cooling 후 구매 개념이 없는 hard block — 우리 P2(소프트 인터셉트) 결정의 반례 |

**관찰 패턴**:

- **5종 모두 가격 게이트가 없다.** 가격 임계로 거르는 경쟁 확장은 발견되지 않았고, 이는 §2 "가격 기반 자동 제외 V1 미지원" 결정과 일치한다. 시장에서도 "특정 금액 이하는 안 막는다"는 정책을 채택하지 않는다.
- **카테고리 자동 분류(생필품/식료품 제외)를 시도하는 확장도 없다.** 휴리스틱 분류의 어려움을 시장이 우회하고 있음을 시사 — §2 "카테고리 자동 분류 V1 미지원"을 뒷받침.
- **트리거는 두 갈래**다: 버튼 단위 인터셉트(Icebox)와 페이지/사이트 단위 차단(Impause·Checkout Chill·Pause). 사이트 단위는 반복·생필품 구매에도 떠 노이즈가 크다 — 우리가 트리거를 "바로구매·결제 버튼"으로 좁힌 이유를 강화한다.
- **명시적 빈도 cap은 드물다.** Checkout Chill의 "결제당 1회"만 명시적이고, 나머지는 cap 없이 사용자 제어(snooze·exclusion)로 노이즈를 흡수한다 — 우리 "동일 URL 1회 + 사용자 제어권" 조합과 같은 방향.
- **사용자 제어권은 Impause가 가장 풍부**하다(snooze·24h 차단·exclusion list). 우리 4축(on/off·24h snooze·skip list·전체 비활성)과 정합한다.

**쿨링오프 차별점**:

- 경쟁 확장은 cooling 기간을 사용자가 임의 지정(Icebox)하거나 고정 30초(Pause)지만, 우리는 **본 서비스 cooling tier(가격별 냉각기)를 그대로 재사용**해 웹·확장이 같은 정책을 공유한다 — 정책 일관성이 차별점.
- 대부분 확장 단독으로 흐름이 끝나지만, 우리는 **인터셉트 → 본 서비스에 항목 등록 → 웹에서 결정**으로 이어지는 통합 루프가 핵심이다.
- 절약 금액·스트릭 등 외재 보상을 노출하는 확장(Icebox)과 달리, 우리는 **결정 중립성을 유지**한다(게이미피케이션 금지 — [`../../README.md`](../../README.md) "만들지 않는 것").
- hard block(StayFocusd 류)과 달리 **소프트 인터셉트**로 결제 흐름을 깨지 않는다.

## 5. 대안 (Considered Alternatives)

- **트리거에 장바구니 포함**: 초안에 포함되어 있었음. 노이즈 우려로 V1에서 제외. Phase 2 후보.
- **카테고리 자동 분류 (생필품/식료품 제외)**: 휴리스틱 false-positive 리스크가 크고, 캡스톤 범위에서 신뢰할 분류기 구축 불가. Phase 2 (`TODO-7`).
- **가격 임계 게이트 (예: 10,000원 미만 통과)**: 초안에 포함되어 있었음. 본 서비스 cooling tier(`../../../pm/prd.md` §4.가격별 냉각기)가 5만원 이하도 1일 cooling을 부여하므로 "cooling 미적용 가격대"가 존재하지 않음. 임의 가격 임계는 본 서비스 정책과 불일치. V1 미지원, Phase 2 (`TODO-9`)에서 사용자가 직접 임계를 정하는 형태로 검토.
- **전역 일일 cap (예: 하루 5회)**: cap 도달 후 진짜 충동구매 시점을 놓침. 빈도는 사용자 제어권으로 우회.
- **결제 흐름 물리적 차단**: TOS 리스크 + 체크아웃 흐름 파손. P2(소프트 인터셉트)와 모순. 영구 제외.
