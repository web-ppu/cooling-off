# 쿨링오프 알림 정책

> 이 문서는 냉각 시간이 끝났을 때 사용자에게 어떻게 알려줄지 정한다.
> 알림은 구매를 설득하는 기능이 아니라, 사용자가 다시 판단하러 돌아오게 만드는 복귀 장치다.

## 1. 결정 요약

알림은 두 가지 성격을 동시에 가진다.

- **판단 관점**: 알림은 보조 기능이다. 알림이 없어도 사용자는 홈에서 결정 대기 항목을 볼 수 있다.
- **복귀 관점**: 알림은 중요하다. 사용자가 냉각이 끝난 시점에 다시 돌아오게 만드는 핵심 장치다.

MVP에서는 이 둘을 헷갈리지 않는다. 알림은 결정을 대신하지 않지만, 사용자가 결정 단계로 돌아오게 만드는 데는 적극적으로 쓴다.

---

## 2. MVP 범위

알림 정책은 아래 제품 동작을 전제로 한다.

| 전제 | 설명 |
|------|------|
| 홈 결정 대기 표시 | 냉각이 끝난 항목은 홈의 결정 대기 섹션에 보인다. |
| 알림 없는 사용 가능성 | 사용자가 알림을 받지 않아도 서비스 핵심 흐름은 막히지 않는다. |

MVP에서 새로 정의하거나 구현할 알림 범위:

| 기능 | 정책 |
|------|------|
| 웹 푸시 | 지원되는 환경에서 냉각 만료 알림을 보낸다. |
| 첫 냉각 시작 직후 권한 제안 | 계정 기준으로 최초 1회만 알림을 제안한다. 두 번째 물건부터는 자동으로 다시 묻지 않는다. |
| iOS 홈 화면 추가 안내 | iOS 미설치 사용자가 푸시를 원하면 홈 화면 추가 방법을 안내한다. |
| 푸시 거부 존중 | 브라우저 권한을 거부하면 푸시를 다시 시도하지 않는다. |
| 중립 카피 | 알림은 [삼]이나 [안 삼] 어느 쪽도 유도하지 않는다. |

MVP 제외 또는 후속 후보:

| 기능 | 처리 |
|------|------|
| 이메일 알림 | Phase 1.5 후보. iOS 보완책이지만 구현 부담이 크다. |
| 재알림 | Phase 2 후보. 첫 출시에서는 냉각 만료 알림만으로 충분한지 먼저 본다. |
| 알림 설정 화면 | Phase 2 후보. 별도 화면 설계가 필요하므로 MVP에서는 만들지 않는다. |
| 채널/종류별 세분화 설정 | Phase 2 후보. 푸시/이메일, 냉각 만료/재알림을 나눠 관리하는 기능이다. |

## 3. MVP 기본 흐름

### 3-1. 알림 제안 시점

알림 제안은 **첫 냉각 시작 직후**에만 보여준다.

MVP에서는 계정 기준으로 첫 물건 등록이 완료된 직후를 기본 트리거로 삼는다. 이 카드는 냉각 항목마다 붙는 기능이 아니다.

한 번이라도 알림 카드를 본 사용자는 두 번째 물건을 등록할 때 자동으로 다시 보지 않는다. 알림을 허용했거나, 거부했거나, 안내를 닫았거나, iOS 설치 안내를 닫은 경우도 모두 반복 노출하지 않는다.

이때가 가장 자연스럽다. 사용자가 방금 물건을 등록했고, "냉각이 끝나면 알려준다"는 말이 바로 이해되기 때문이다.

노출하지 않는 시점:

- 첫 방문 직후
- 로그인 직후
- About 페이지 진입 시
- 홈에 그냥 들어왔을 때
- AI 채팅 화면 진입 시

### 3-2. 권한 제안 카드

Android, 데스크톱, 이미 설치된 iOS PWA에서는 아래 카드를 쓴다.

| 요소 | 문구 |
|------|------|
| 제목 | 냉각이 끝나면 알려드릴까요? |
| 설명 | `{결정 가능 날짜}`부터 다시 결정할 수 있어요. 푸시를 허용하면 그때 알려드릴게요. 선택하지 않아도 홈에서 확인할 수 있습니다. |
| 주요 버튼 | 푸시로 받기 |
| 거부 버튼 | 괜찮아요 |

여기서 `{결정 가능 날짜}`는 실제 냉각 종료 시각이다. 예: `5월 29일 14:00`.

상품명, 가격, URL, 사고 싶은 이유는 이 카드에 다시 강조하지 않는다. 등록 직후라 사용자가 이미 알고 있고, 구매 욕구를 다시 키울 필요가 없다.

iOS Safari 탭에서 아직 PWA로 설치하지 않은 경우에는 별도 카드를 쓴다. 이 경우 푸시 권한을 바로 요청할 수 없기 때문이다.

| 요소 | 문구 |
|------|------|
| 제목 | iPhone에서는 홈 화면에 추가하면 알림을 받을 수 있어요 |
| 설명 | `{결정 가능 날짜}`부터 다시 결정할 수 있어요. 설치하지 않아도 홈에서 확인할 수 있습니다. |
| 주요 버튼 | 홈 화면에 추가하고 알림 받기 |
| 보조 버튼 | 그냥 홈에서 확인할게요 |

이 카드는 설치를 강요하는 화면이 아니다. 사용자가 푸시를 받고 싶을 때만 설치 안내로 넘어가고, 원하지 않으면 홈에서 수동 확인하는 흐름으로 닫힌다.

### 3-3. 푸시 권한 처리

Android, 데스크톱, 이미 설치된 iOS PWA:

1. 사용자가 `푸시로 받기`를 누른다.
2. 브라우저 권한 팝업을 띄운다.
3. 허용하면 푸시 구독을 저장한다.
4. 거부하면 푸시는 더 시도하지 않고 알림 제안 상태를 `거부`로 저장한다.
5. 거부해도 홈의 결정 대기 상태는 그대로 동작한다.

iOS Safari 탭, 미설치:

1. 사용자가 `홈 화면에 추가하고 알림 받기`를 누른다.
2. 알림 제안 상태를 `iOS 설치 안내 진행`으로 저장한다.
3. iOS 설치 안내 바텀시트를 보여준다.
4. 이 시점에는 푸시 권한 팝업을 띄우지 않는다.
5. 사용자가 홈 화면 아이콘으로 다시 들어오면 `알림 켜기`를 보여준다.
6. 그때 브라우저 권한 팝업을 띄운다.
7. 사용자가 설치 안내를 닫으면 알림 제안 상태를 `닫음`으로 저장한다.
8. 사용자가 설치 안내를 닫아도 홈의 결정 대기 상태는 그대로 동작한다.

### 3-4. 화면 반영 위치

알림 제안의 주 화면은 **첫 등록 완료 직후의 홈**이다. 현재 제품 흐름은 등록이 끝나면 홈으로 돌아오므로, 홈의 문서 헤더 아래이자 결정 대기/냉각 중 목록 위에 1회성 카드를 둔다.

| 화면/위치 | 처리 |
|-----------|------|
| 등록 화면 | 폼 작성과 냉각 시작에 집중한다. 푸시 권한 요청을 폼 안에 끼우지 않는다. |
| 첫 등록 완료 직후 홈 | 주 노출 위치. 방금 시작된 냉각 항목의 결정 가능 시점을 함께 보여준다. |
| 두 번째 이후 등록 완료 직후 홈 | 알림 카드를 다시 띄우지 않는다. |
| 홈 일반 진입 | 알림 카드를 새로 띄우지 않는다. 홈은 결정 대기/냉각 중 확인 화면으로 유지한다. |
| 냉각 중 화면 | 알림 권한 제안 카드를 두지 않는다. 알림을 이미 허용한 경우에만 "결정 가능 시점이 되면 알려드릴게요" 같은 문구를 쓸 수 있다. |
| About | 알림 권한 요청, iOS 설치 안내, 알림 끄기 토글을 넣지 않는다. |

카드는 목록 카드 안에 넣지 않는다. 알림 제안은 특정 물건의 상세 정보가 아니라, 냉각 종료 시점에 다시 돌아오기 위한 계정 단위 선택이기 때문이다.

### 3-5. 알림 제안 상태

MVP에서도 알림 카드 노출 여부는 물건이 아니라 계정 단위로 저장한다. 반대로 푸시 구독은 기기와 브라우저마다 다를 수 있으므로 별도로 저장한다.

| 데이터 | 저장 단위 | 의미 |
|------|-----------|------|
| 알림 제안 상태 | 계정 | 알림 카드를 이미 보여줬는지, 사용자가 허용/거부/닫음 중 무엇을 선택했는지 |
| 푸시 권한 상태 | 브라우저 | 브라우저가 가진 `Notification.permission` 값 |
| 푸시 구독 | 기기/브라우저 | 실제 푸시를 보낼 endpoint와 key |

알림 제안 상태:

| 상태 | 의미 | 다음 등록 때 |
|------|------|--------------|
| 미노출 | 아직 알림 카드를 보여준 적 없음 | 첫 등록 완료 직후 1회 노출 |
| 허용 | 푸시 구독 저장 완료 | 다시 묻지 않음 |
| 거부 | 권한 카드 또는 브라우저 권한 팝업에서 거부 | 다시 묻지 않음 |
| 닫음 | 카드나 iOS 설치 안내를 닫음 | 다시 묻지 않음 |
| iOS 설치 안내 진행 | 사용자가 홈 화면 추가 안내를 열었음 | PWA 재진입 조건을 만족할 때 `알림 켜기`만 이어서 표시 |

MVP에는 알림 설정 화면이 없다. 그래서 사용자가 알림 제안을 닫은 뒤 다시 켜는 진입은 제공하지 않는다. 신뢰를 위해 자동 재노출을 하지 않는 대신, 재활성화 진입이 없는 리스크는 MVP에서 감수한다. 다시 켜는 흐름은 Phase 2 설정 화면에서 다룬다.

### 3-6. iOS 설치 안내 바텀시트

iOS Safari 미설치 사용자가 `홈 화면에 추가하고 알림 받기`를 선택하면 바텀시트를 연다.

| 요소 | 문구 |
|------|------|
| 제목 | 알림을 받으려면 홈 화면에 추가해야 해요 |
| 설명 | iPhone에서는 Safari 탭이 아니라 홈 화면 아이콘으로 들어왔을 때 알림을 켤 수 있어요. |
| 1단계 | Safari 하단 또는 상단의 공유 버튼을 누르세요. |
| 2단계 | `홈 화면에 추가`를 선택하세요. |
| 3단계 | `추가`를 누르세요. |
| 4단계 | 홈 화면의 쿨링오프 아이콘으로 다시 들어오면 알림을 켤 수 있어요. |
| 닫기 버튼 | 그냥 홈에서 확인할게요 |

이 바텀시트의 목적은 앱 설치를 늘리는 것이 아니다. "설치하면 더 좋아요"가 아니라 **"알림을 받으려면 이 과정이 필요해요"**로 말한다.

### 3-7. iOS PWA 재진입 조건

iOS 설치 안내를 본 사용자가 홈 화면 아이콘으로 다시 들어오면, 아래 조건을 모두 만족할 때만 `알림 켜기` 카드를 보여준다.

| 조건 | 이유 |
|------|------|
| iOS/iPadOS 환경 | iOS 홈 화면 추가 안내에서 이어지는 흐름이기 때문 |
| PWA 실행 상태 | Safari 탭이 아니라 홈 화면 아이콘으로 들어온 상태여야 푸시 권한을 요청할 수 있음 |
| 알림 제안 상태가 `iOS 설치 안내 진행` | 사용자가 먼저 알림을 받겠다고 선택한 흐름이어야 함 |
| 브라우저 권한이 아직 `default` | 이미 허용했거나 거부한 상태에서는 다시 권한 팝업을 띄우지 않음 |
| Push API와 Service Worker 사용 가능 | 실제 구독 저장까지 이어질 수 있어야 함 |

PWA 실행 상태는 `display-mode: standalone` 또는 iOS의 standalone 실행 여부로 판단한다.

## 4. 플랫폼별 정책

### 4-1. Android / 데스크톱

MVP의 1차 대상이다. 브라우저 푸시를 바로 제안한다.

| 상황 | 처리 |
|------|------|
| 푸시 지원 | `푸시로 받기` 버튼 표시 |
| 푸시 허용 | 푸시 구독 저장 |
| 푸시 거부 | 다음 세션과 다음 등록에서도 다시 묻지 않음 |
| 푸시 미지원 | 알림 없이 홈에서 확인 가능하다고 안내 |

### 4-2. iOS Safari 탭, 미설치

iOS 미설치 사용자는 푸시를 바로 켤 수 없다. 다만 홈 화면 추가 자체가 오래 걸리는 작업은 아니므로, 푸시를 원하는 사용자에게는 MVP에서 설치 안내를 제공한다.

중요한 점은 설치를 강제하지 않는 것이다. 사용자는 `홈 화면에 추가하고 알림 받기`와 `그냥 홈에서 확인할게요` 중 하나를 고른다.

| 상황 | 처리 |
|------|------|
| 푸시를 원함 | iOS 설치 안내 바텀시트 표시 |
| 설치 후 PWA로 재진입 | `알림 켜기` 버튼 표시 |
| 설치 안내 닫음 | 홈에서 확인 가능하다고 안내하고 종료 |
| 설치하지 않음 | 냉각 만료 후 홈의 결정 대기 섹션에서 확인 |

즉, MVP 정책은 "iOS는 미지원이라 포기"가 아니다. **설치 선택지는 제공하되, 설치하지 않는 흐름도 정상 흐름으로 둔다.**

### 4-3. iOS PWA, 이미 설치됨

이미 홈 화면에서 실행 중이면 푸시를 제안할 수 있다.

| 상황 | 처리 |
|------|------|
| PWA로 실행 중 | `푸시로 받기` 버튼 표시 |
| 푸시 허용 | 푸시 구독 저장 |
| 푸시 거부 | 다음 세션과 다음 등록에서도 다시 묻지 않음 |

## 5. 냉각 만료 알림

MVP에서 보내는 알림은 냉각 만료 알림 하나다.

| 항목 | 정책 |
|------|------|
| 트리거 | 물건의 냉각 시간이 끝나 결정 대기 상태가 된 시점 |
| 제외 | 비로그인, 이미 결정함, 삭제됨, 알림 끔, 푸시 미동의 |
| 빈도 | 물건당 1회 |
| 발송 시간 | KST 22:00~08:00에는 보내지 않고 다음 08:00 이후로 미룸 |
| 이동 | 알림 선택 시 홈의 결정 대기 섹션으로 이동 |
| 사용자 제어 | MVP에서는 권한 제안 거부와 브라우저/OS 권한 해제로 처리. 인앱 알림 설정은 Phase 2 |

알림 문구:

| 요소 | 문구 |
|------|------|
| 제목 | 결정할 시간입니다 |
| 본문 | 냉각 시간이 끝났습니다. 준비되면 확인해보세요. |
| 액션 | 결정하러 가기 |

알림에는 넣지 않는다:

- 가격
- URL
- 사고 싶은 이유
- 상품 이미지
- 절약 금액
- 결정 대기 개수 강조
- [삼] 또는 [안 삼]을 유도하는 말

---

## 6. 알림 설정 화면

MVP에서는 별도 알림 설정 화면을 만들지 않는다. 알림 설정은 화면 하나가 새로 필요한 기능이고, 저장 구조와 디자인도 같이 필요하기 때문이다.

MVP에서 제공하는 제어는 여기까지다.

| 상황 | 처리 |
|------|------|
| 권한 제안 카드에서 거부 | 다음 세션과 다음 등록에서도 다시 묻지 않는다. |
| 브라우저 권한 팝업에서 거부 | 푸시를 다시 시도하지 않는다. |
| 이미 허용한 푸시를 끄고 싶음 | MVP에서는 브라우저/OS 알림 설정에서 끄는 것으로 둔다. |

Phase 2에서는 별도 알림 설정 화면을 만든다.

| 항목 | 정책 |
|------|------|
| 화면 위치 | 별도 설정 화면을 둔다. 예: `/settings/notifications` |
| About의 역할 | 설정을 직접 담지 않는다. 필요하면 설정 화면으로 가는 링크만 둔다. |
| 최소 기능 | 알림 켜기/끄기 |
| 확장 기능 | 푸시/이메일 채널별 설정, 냉각 만료/재알림 종류별 설정 |

About 페이지에 알림 토글을 직접 넣지 않는 이유:

- About은 서비스 설명 페이지다.
- 알림 설정은 사용자 계정/기기 상태를 다루는 조작 화면이다.
- About에 넣으면 화면 목적이 흐려진다.
- 설정 화면 디자인과 상태 저장까지 같이 필요해져 MVP 범위가 커진다.

## 7. Phase 1.5: 이메일 알림 후보

이메일은 iOS 미설치 사용자를 보완할 수 있지만 MVP 필수 범위는 아니다. 발송, 수신 동의, 해지, 실패 처리까지 같이 책임져야 하기 때문이다.

| 트리거 | 의미 |
|--------|------|
| iOS 사용자가 많고 PWA 설치 선택률이 낮다 | 웹 푸시만으로는 iOS 복귀 장치가 부족함 |
| 사용자 테스트에서 "알림이 안 와서 잊었다"는 피드백이 반복된다 | 홈 수동 확인만으로 부족함 |
| 구현 여력이 충분하다 | 발송/동의/해지까지 책임질 수 있음 |

이메일을 넣는다면 지킬 규칙:

- 이메일은 사용자가 `이메일로 받기`를 직접 선택했을 때만 보낸다.
- Google 로그인으로 이메일 주소를 확보한 것은 발송 동의가 아니다.
- 푸시를 거부했다고 이메일을 자동으로 보내지 않는다.
- 푸시와 이메일을 동시에 보내지 않는다.

---

## 8. Phase 2: 재알림 후보

재알림은 첫 출시에서 바로 넣지 않는다. 먼저 냉각 만료 알림만으로 사용자가 돌아오는지 본다.

| 트리거 | 의미 |
|--------|------|
| 냉각 만료 알림 클릭률은 있는데 결정 완료율이 낮다 | 사용자가 한 번 보고도 결정하지 않음 |
| 결정 대기 항목이 오래 쌓인다 | 한 번의 알림으로 복귀가 부족함 |
| 사용자 인터뷰에서 "놓쳤다"는 말이 나온다 | 재상기가 실제 도움이 될 수 있음 |

재알림을 넣더라도 원칙은 유지한다. 같은 결정 대기 상태에는 1회만 보내고, 압박하는 문구나 절약 강조는 쓰지 않는다.

---

## 9. Phase 2: iOS 설치 안내 개선 후보

MVP에도 iOS 홈 화면 추가 안내 바텀시트는 넣는다. 다만 첫 버전에서는 텍스트 중심 안내로 단순하게 만든다.

Phase 2에서 검토할 것은 "설치 유도 여부"가 아니라 "설치 안내를 얼마나 친절하게 개선할지"다.

아래 신호가 있으면 개선한다.

| 트리거 | 의미 |
|--------|------|
| `홈 화면에 추가하고 알림 받기` 클릭 후 재진입률이 낮다 | 사용자가 설치 과정에서 이탈함 |
| 사용자 테스트에서 Safari 공유 버튼을 못 찾는다 | 안내 UI가 부족함 |
| iOS 복귀율이 Android/데스크톱보다 낮다 | iOS 알림 경로 개선 필요 |

개선 후보:

- Safari 공유 버튼 위치를 보여주는 이미지
- 짧은 화면 예시
- 설치 후 재진입 상태 복구 고도화

## 10. 카피 가이드

알림과 권한 요청 UI는 시스템 UI와 같은 존댓말을 쓴다. AI 채팅의 반말과 섞지 않는다.

| 상황 | 쓰지 않음 | 사용 |
|------|-----------|------|
| 결정 대기 | 결정 안 한 게 4개나 쌓였어요! | 결정할 항목이 기다리고 있어요. |
| 행동 유도 | 지금 정리하세요! | 준비되면 확인해보세요. |
| 구매 방향 | 안 사러 가기 / 사러 가기 | 결정하러 가기 |
| 보상 | 잘 참으셨어요 / 이만큼 절약했어요 | 보상 표현 없음 |
| 거부 버튼 | 알림 없이 괜찮겠어요? / 나중에 | 괜찮아요 |
| 재알림 | 아직도 결정 안 하셨어요? | 준비되면 쿨링오프에서 확인해보세요. |

버튼 문구:

| 상황 | 버튼 |
|------|------|
| 푸시 가능 | 푸시로 받기 |
| iOS 홈 화면 추가 | 홈 화면에 추가하고 알림 받기 |
| iOS 홈 화면 추가 보류 | 그냥 홈에서 확인할게요 |
| 거부 | 괜찮아요 |
| 알림 선택 후 이동 | 결정하러 가기 |
| Phase 1.5 이메일 | 이메일로 받기 |

## 11. 성공 지표

알림 기능은 권한 허용률만 보면 안 된다. 중요한 것은 사용자가 냉각 종료 후 다시 돌아와 실제로 결정하는지다.

MVP에서 볼 지표:

| 지표 | 보는 이유 |
|------|-----------|
| 알림 카드 노출 수 | 권한 제안이 실제로 얼마나 발생하는지 |
| 푸시 허용률 | 사용자가 알림을 받을 의사가 있는지 |
| 푸시 거부율 | 권한 요청 타이밍이나 문구가 부담스러운지 |
| iOS 설치 안내 클릭률 | iOS 사용자가 푸시를 받기 위한 절차를 시작하는지 |
| iOS 설치 안내 닫힘률 | 설치 안내가 부담스럽거나 이해하기 어려운지 |
| iOS PWA 재진입률 | 홈 화면 추가 안내가 실제 재진입으로 이어지는지 |
| iOS PWA 재진입 후 알림 켜기 클릭률 | 설치 후 푸시 권한 요청까지 이어지는지 |
| 냉각 만료 알림 발송 수 | 시스템이 실제로 동작하는지 |
| 알림 클릭률 | 알림이 복귀를 만들고 있는지 |
| 냉각 만료 후 결정 완료율 | 알림 이후 핵심 행동까지 이어지는지 |
| 푸시 권한 해제/구독 해제 신호 | 알림이 귀찮게 느껴지는지. MVP에서는 정밀 측정이 어려우면 Phase 2에서 본다. |

판단 기준:

- 푸시 허용률이 낮으면 권한 제안 타이밍과 문구를 다시 본다.
- 알림 클릭률이 낮으면 알림 문구와 발송 시간을 다시 본다.
- 클릭률은 있는데 결정 완료율이 낮으면 AI 채팅 진입 또는 결정 화면 흐름을 다시 본다.
- 결정 대기 항목이 계속 쌓이면 Phase 2 재알림을 검토한다.

## 12. 개발 위임 사항

아래는 정책을 구현으로 넘길 때 지켜야 하는 제품 계약이다. Cron, VAPID, Service Worker 같은 구체 구현은 [`tech-spec.md`](../engineering/tech-spec.md)에서 관리한다.

MVP:

- 첫 등록 완료 직후 홈 상단 알림 카드
- 등록 성공 후 홈에서 방금 시작된 냉각 항목을 식별하는 전달 방식
- 계정 기준 알림 제안 상태 저장
- 기기/브라우저 기준 푸시 구독 저장
- iOS 설치 안내 바텀시트
- iOS 설치 안내 후 PWA 재진입 조건을 만족할 때만 `알림 켜기` 표시
- 야간 발송 제한
- 물건당 냉각 만료 알림 1회 제한

Phase 1.5 이후:

- 이메일 알림
- iOS 설치 안내 개선
- 알림 설정 화면
- 재알림
