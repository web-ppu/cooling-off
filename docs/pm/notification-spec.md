# 쿨링오프 푸시 알림 기획서

PRD FR-8 과 screen-spec §4 를 기반으로, 운영 합의 사항을 반영한 알림 기능의 확정 사양입니다.
추후 기획 업데이트가 필요하면 본 문서를 출발점으로 갱신합니다.

- 상위 문서: `docs/pm/prd.md` (FR-8), `docs/design/screen-spec.md` (§4 알림 정책)
- 최초 작성: 2026-05-26
- 버전: v1

---

## 1. 발송 채널

| 항목 | 결정 |
|---|---|
| 채널 | Web Push 단일 |
| 지원 플랫폼 | Android, iOS, PC (브라우저) |
| 기반 인프라 | `web-push` 라이브러리 + Service Worker (`public/sw.js`) + DB `push_subscriptions` |

### iOS 특이 제약

iOS Safari 는 "홈 화면에 추가(PWA)" 된 사이트만 web push 수신이 가능합니다 (iOS 16.4+). 일반 Safari 탭에서는 푸시가 전달되지 않습니다.

iOS 사용자가 알림을 받으려면 다음 절차가 필요합니다:

1. 사이트 진입
2. Safari 공유 메뉴 → "홈 화면에 추가"
3. 홈 화면 아이콘으로 접속

> 안내 UI 위치·문구는 별도 결정 필요 (개발 단계에서 확정).

## 2. 알림 발송 스케줄

### 발송 주기

- **매일 1회**, 특정 시각에 발송
- 구체 시각(예: 19:00 KST) 은 별도 결정 필요

### 발송 조건

- 발송 시각 기준 **5분 전** 시점에 사용자별 `items` 테이블 조회
- `status = 'ready' AND deleted_at IS NULL` 인 항목이 **1개 이상** → 발송
- **0개** → 발송하지 않음
- 5분 윈도우의 의미: 발송 직전 상태 확정 + 실제 발송 처리 시간 확보

### 발송 단위

- 사용자별 1건. 해당 사용자의 ready 항목이 여러 개여도 알림은 1건만 발송
- 메시지 분기는 ready 항목 개수에 따라 결정 (§3 참고)

## 3. 알림 내용

`docs/design/screen-spec.md` §4 표 그대로 따른다.

| 상황 | 제목 | 내용 |
|---|---|---|
| ready 1건 | `결정할 시간입니다` | `냉각 시간이 끝났습니다. 지금 다시 판단해 보세요.` |
| ready 2건 이상 | `결정할 물건이 있습니다` | `냉각 시간이 끝난 물건이 있습니다. 지금 다시 판단해 보세요.` |

### 문구 제약

- **포함 금지**: 가격, URL, 사고 싶은 이유, 이미지, 항목 이름
- **포함 권장**: 존댓말, 중립 톤
- 의도: 충동 재자극 방지

## 4. 권한 요청 / 거부 흐름

### 정책 (운영 합의 사항)

- 항목 등록 시점에 다음 배너를 표시:
  - 배너 문구: `"냉각 시간이 끝나면 알려드릴게요."`
  - **[알림 받기] 버튼은 제공하지 않음** — 사용자 명시 동의 절차 없음
- 등록된 항목은 **무조건** ready 도달 시 알림 발송 대상

### 권한 거부 시

- 알림이 발송되지 않을 뿐, 서비스 본 기능에는 영향 없음
- ready 항목은 홈의 결정 대기 섹션에 정상 표시 (`screen-spec.md` §4 정책 그대로)

### 권한 획득의 기술적 처리 방향

브라우저는 `Notification.requestPermission()` 호출 시점에만 권한 팝업을 표시합니다. 별도 [알림 받기] 버튼 없이 권한을 받기 위한 후보:

1. 배너 표시 직후 자동으로 `requestPermission()` 호출
2. 등록 폼 [냉각 시작] 클릭이 user gesture 로 인정되는 점을 이용해 함께 트리거
3. 배너 자체를 클릭 가능한 영역으로 처리

운영 합의: **옵션 2 권장** — 등록 폼 제출이 곧 동의로 해석. 사용자 정의 정책과도 부합. 다만 구현 단계에서 브라우저별 동작 검증 후 최종 확정.

## 5. 알림 클릭 동작

| 상황 | 이동 |
|---|---|
| 로그인 상태 | `/` (홈) — 결정 대기 섹션 우선 노출 |
| 세션 만료 | `/login` → 로그인 성공 후 `/` 의 결정 대기 섹션 |

`public/sw.js` 의 `notificationclick` 핸들러가 `event.notification.data.url` 로 이동시키므로, 발송 측에서 적절한 URL 을 함께 보내면 됩니다.

## 6. 실패 / 재시도 정책

### 정책

- 발송 실패 시 **1시간 간격** 으로 재시도
- **최대 3회** 재시도
- 3회 모두 실패하면 **당일은 발송 중단**, 다음 날 다시 시도

### "실패" 단위 정의 — 구현 단계에서 확정 필요

| 시나리오 | 처리 방향 |
|---|---|
| Cron 자체가 안 도는 경우 (Vercel cron 실패) | 1시간 후 재시도 |
| 전체 사용자 발송이 실패 (DB 접근 불가 등) | 1시간 후 재시도 |
| 일부 사용자만 발송 실패 (해당 endpoint 일시적 오류) | 사용자별 재시도 권장 — 구현 단계에서 확정 |
| 410 Gone (구독 만료) | 재시도 무의미 — `push_subscriptions` 에서 즉시 삭제 |
| 429 / 5xx 일시적 오류 | 1시간 후 재시도 대상 |

**제안 해석** (사양 침묵 영역):

- 재시도 단위는 사용자별 (per-subscription) 로 추적
- 410 Gone 만 즉시 삭제 (재시도 안 함)
- 그 외 모든 실패는 사용자별로 retryCount 누적 → 3회 도달 시 당일 포기

## 7. 데이터 모델

### 현재 schema (`supabase/schema.sql`)

```sql
push_subscriptions
├── id (uuid)
├── user_id (uuid, FK auth.users)
├── endpoint (text)
├── p256dh (text)
├── auth (text)
├── created_at (timestamptz)
└── UNIQUE (user_id, endpoint)
```

RLS 정책으로 사용자별 격리됨.

### 추가 필요할 수 있는 자료 구조

재시도 추적 구현 방식에 따라 다음 중 선택:

| 후보 | 용도 |
|---|---|
| 별도 테이블 `notification_attempts` | 사용자·날짜별 시도 횟수·결과 추적 |
| `push_subscriptions.last_error_at`, `last_error_count` 컬럼 추가 | subscription 단위로 누적 |
| Redis / KV | 휘발성 카운터 (당일만 유지) |

→ 구현 단계에서 확정.

## 8. 발송 트리거 인프라

### 후보

- **Vercel Cron** — `vercel.ts` 의 `crons:` 필드. 분 단위 정밀도 가능
- Supabase Edge Function + `pg_cron` — DB 쪽에서 트리거. 정확도 높지만 셋업 복잡

**권장**: Vercel Cron. 매일 결정된 시각에 `/api/cron/send-notifications` 호출.

### 재시도 트리거

- 메인 Cron 이 실패 정보를 저장소(§7) 에 기록
- 시간별 Cron (`0 * * * *`) 이 기록을 보고 재시도

또는 메인 Cron 내부에서 await retry 루프 — 함수 timeout 위험으로 비권장.

## 9. 구현 시작 전 결정 필요 항목

본 사양을 코드로 옮기기 전에 다음 5가지 확정 필요:

1. **발송 시각** — 매일 몇 시? (예: 19:00 KST 등)
2. **iOS PWA 안내 정책** — 안내 UI 위치·문구, 또는 안내 없이 진행 여부
3. **재시도 단위** — 사용자별 vs 배치 전체
4. **재시도 추적 저장소** — 별도 테이블 / 기존 컬럼 / Redis
5. **시간대 처리** — 모든 사용자 KST 통일 / 향후 사용자 시간대 지원 여지

## 10. PRD / screen-spec 과의 정합성

본 기획서는 다음 두 상위 문서를 충실히 따른다:

- PRD FR-8: "냉각기가 끝났음을 알려 사용자가 다시 판단하러 돌아오게 한다", "알림 제공 방식은 개발 단계에서 확정"
- PRD §8 MVP 포함: "냉각기 만료 알림"
- screen-spec §4: 알림 정책 표 + 문구 제약 + 권한·거부 흐름

PRD §8 Phase 2 후보의 "홈 화면 배지 등 보조 알림" 은 본 기획 범위에서 제외.
